## Protocolo

El cliente del servidor enviará una línea JSON por socket Unix local. La solicitud contiene ID de petición y decisión, versión del estado, esfuerzo `low|medium|high`, asiento, mano propia, estado público resumido, historial acotado y las opciones que el servidor ya considera legales. El protocolo rechaza campos adicionales, nombres, texto libre, roles/acciones desconocidos, IDs repetidos y contextos mayores de 48 KiB. El modelo fijo es `gpt-6-luna`; la salida tiene un único `choiceId` que debe corresponder a una opción actual.

La respuesta repite los IDs/versiones de la solicitud y la versión de reglas `b189cc0`. El cliente compara todos esos valores y comprueba de nuevo que la opción exista. Un resultado inválido, tardío, desactualizado o de otra regla no modifica el juego. El servidor de runner atiende como máximo dos decisiones a la vez, limita solicitudes y errores, y cancela el proceso si vence el plazo o el cliente desaparece.

## Reglas y estilo

La fuente normativa es `docs/coup_transcription.md`; `docs/coup_play_reference.md`, `docs/coup_summary_card.md` y `docs/coup_llm_summary.md` son sus referencias derivadas, versionadas en el commit `b189cc0`. El prompt fijo incorpora las reglas operativas necesarias para decidir, señala esa versión y pide juego adaptable: mentir cuando compense, decir la verdad cuando convenga y desafiar según evidencia, nunca usar una estrategia de mentira permanente. Recuerda que una carta probada vuelve a Court y se reemplaza; una afirmación no desafiada no demuestra que el jugador tuviera la carta.

El prompt solo procesa campos enumerados por el contrato; no carga los Markdown ni el checkout. La mano privada se limita al asiento que decide. Cada llamada es efímera y sin memoria compartida deliberada entre asientos. El modelo devuelve una elección, nunca una transición: el servidor continúa como autoridad de reglas, costos, bloqueos, desafíos, pérdidas y turno.

La prioridad digital aprobada para desafíos/bloqueos simultáneos es el primer asiento elegible en sentido horario desde quien declaró la acción o bloqueo; no depende de la latencia. Está escrita en `docs/plans/codex-ai-players/f0_contract.md` y ya tiene regresiones F1 para desafíos y bloqueos concurrentes.

## Frontera de procesos

En despliegue, la aplicación web no tendrá `CODEX_HOME`, la sesión Plus ni permisos para leer su caché. Se ejecutará un proceso `coup-codex` separado, sin privilegios, conectado por `/run/coup-codex/runner.sock` con permisos de grupo limitados. Su código se instalará fuera del checkout web; el servicio ocultará el checkout con `InaccessiblePaths`, usará `/run/coup-codex-work` vacío y de solo lectura, HOME igual a ese directorio, `CODEX_HOME` separado, `PrivateTmp` y `ProtectSystem=strict`. La unidad usa `UMask=0077` para que los temporales/sockets internos de Codex sean privados; el worker aplica luego modo `0660` al socket IPC que comparte con el grupo del juego. `server/ai/coup-codex-runner.service.example` es una plantilla: el path canónico del checkout y el grupo se completan en Issue #13. La sesión queda en `/var/lib/coup-codex/auth`, protegida por el usuario de servicio; el archivo `auth.json` se trata como contraseña.

La primera prueba con `--sandbox read-only` pudo leer un archivo señuelo situado fuera del workspace. Ese modo no protege la caché Plus por sí solo. El perfil inline niega `:root`, concede lectura a `:minimal` y al workspace actual, y permite escritura solo en el temporal privado (`/run/coup-codex/tmp`). No fija `:slash_tmp`: la guía define `/tmp` como path separado y deja paths no declarados sin acceso; la denegación de `:root` sigue cerrando esa ruta fuera de la concesión específica de `:tmpdir`. La prueba mostró que añadir explícitamente `:slash_tmp=deny` o `write` impedía preparar el socket interno, mientras omitir esa entrada permitía correr el sandbox. La red para comandos está deshabilitada y shell/apps/subagentes/hooks apagados. El servicio asigna paths privados separados: `TMPDIR=/run/coup-codex/tmp` para scratch/bubblewrap y `XDG_RUNTIME_DIR=/run/coup-codex/runtime` para runtime/socket; el proceso valida que ambos existan, sean distintos, y no tengan bits de grupo/otros. No pasa `--sandbox`, ya que los perfiles de permisos no se combinan con el modo sandbox anterior.

Los dos PHASE anteriores no completaron la prueba Linux: registraron un error de directorio de socket interno y el perfil explícito con `:slash_tmp` falló antes del comando. Un probe local posterior sin autenticación con CLI `0.157.1` y directorios `TMPDIR`/`XDG_RUNTIME_DIR` separados leyó el marcador permitido, no pudo leer un señuelo de auth, rechazó escritura en workspace y permitió escritura en TMPDIR. El tercer PHASE (`d74e71c`) no reprodujo ese resultado: volvió a fallar antes de `/bin/cat` con `app-server socket directory must be a user-owned directory with mode 0700`. Los paths señuelo eran distintos, privados y del mismo usuario. ## Compatibilidad del login Plus y gate abierto

La documentación oficial describe `codex exec` para automatización, permite `--output-schema` y reutiliza auth guardada. También advierte: no usar el flujo avanzado de auth gestionada por ChatGPT para repositorios públicos/open source. Coup Online es público. El runner no monta el repo y recibe únicamente JSON del juego, pero la guía no declara que esto constituya una excepción; no se habilitará auth Plus hasta aclarar esta aplicabilidad. No habrá API ni fallback.

La documentación oficial de precios lista GPT-6 Luna y Codex CLI para Plus. La guía de modelos indica que la disponibilidad concreta depende del rollout, método de inicio de sesión y cliente. Su recomendación de Sol para Plus aplica al reemplazo de GPT-5.5, no demuestra que Luna no forme parte del plan. La cuenta/CLI concreta no se ha verificado porque no hay login autorizado en F2. Luna permanece fija y, si no aparece disponible, no se invoca nada ni hay fallback.
